# 0.6 implementation and qualification status

The optional [local companion](LOCAL-COMPANION-0.6.md) adds loopback-native browser participation and a VS Code browser-opening command without changing core event semantics. Standalone runtime packaging is distinct from target qualification: cross-built Windows executables still require Windows CI execution and endpoint/signing approval. No public CI workflows are introduced. Browser tests simulate unavailable directory access; they do not certify every managed Edge policy configuration.

Date: 2026-10-16. Status: **development branch; not cleared for publication or the professional pilot**.

Creation now offers independently selected Windows x64, macOS Apple Silicon and Linux x64 Node companions. The shared authoring service resolves exact pinned artifacts before core publication; the creation form and CLI use that service. A client-owned catalog binds companion/toolbox code, runtime/executable digests, sizes and build receipts. Private verified cache reuse avoids repeated downloads. Distinct platform names coexist beside one immutable manifest/event history. The VSIX contains only the catalog, not all platform runtimes. See [delivery details](../docs/COMPANION-DELIVERY.md). Release URLs remain unavailable until those exact candidate artifacts are explicitly published; development checkouts can use their verified local distributions.

The security-remediation run passes 180 unit/core tests, 14 browser scenarios, the full local macOS VS Code suite and an independent upstream Slidev-parser parity test. The complete application dependency audit reports zero vulnerabilities without exceptions. The isolated trusted Slidev fixture has one explicitly approved braces advisory bound to its lockfile/versions and expiring 15 November 2026; it is not audit-clean. See the [dated security review](../docs/DEPENDENCY-SECURITY.md). Native artifacts are rebuilt/re-pinned after runtime changes and require fresh target-platform qualification. These local results do not close signing, endpoint, performance or publication gates.

This report distinguishes implemented behavior from qualification evidence. Package and wire version 0.6.0 identify the development candidate; they do not claim that all acceptance gates have passed. No remote push, merge or release is implied by a local build.

## Implemented architecture

`src/professional/` contains the shared exact-byte parser, precompiled schemas, graph/lifecycle/policy rules, rooted storage adapters, review sessions, authoring service, CLI, Markdown/source mapping, reviewer toolbox and audit exporter. The portable HTML and VS Code webview run the same toolbox. Only storage access and author-only source operations differ by host.

New review creation always emits a review-named HTML entry file bound to the review ID and exact manifest digest, without embedding reviewed content or events. Browsers open it directly, grant the adjacent folder once, and automatically reconnect only when the browser reports permission already granted; VS Code opens the same file through a custom editor. The VS Code extension uses its installed trusted client code when reading a received package. CLI creation calls the same authoring service, not VS Code automation.

Cold open now exposes manifest/event/rendering progress immediately and implements the partial-revision rule in VALID-05 for ordinary Markdown: descriptors and policy are admitted first, anchored-event validation fetches only referenced documents, and the visible document fetches only its used resources. Optional presentation profiles load their required profile evidence up front. Fresh approval/audit paths continue reading and verifying the complete required content set.

VS Code can publish an existing package to an empty shared/synchronized/Git destination using an exact link-free inventory, streaming hashes, exclusive destination files, manifest-last visibility, source recheck and full destination validation. It then switches to the destination and leaves the original disconnected on disk. Received or moved reviews use an explicit private source-link command that reports exact/changed/missing head documents; revising no longer falls back to the first unrelated workspace. Protocol 0.6 still has one Markdown source root, selected explicitly in multi-root workspaces.

The 0.4 reader is retained in VS Code without migration. The shared professional reader selects exact 0.5 or 0.6 schemas from the immutable manifest and does not reinterpret older packages using new lifecycle rules.

The 0.6 development line adds a shared creator resolution workbench and the required `thread-addressing-v1` capability to protocol 0.6 packages. It records exact descendant-revision implementation evidence and causal reviewer verification/challenge events. VS Code source navigation uses only the private source binding; the browser sees and writes the same shared workflow events but never receives a native source path. Existing 0.5 packages remain readable and cannot emit the new event families.

Creation optionally accepts an immutable email roster (`reviewer-roster-v1`) through the VS Code form or repeatable CLI flags. The shared core maps canonical emails to stable IDs and rejects out-of-roster actors. New reference packages require `reviewer-completion-v1`: exact-inventory-backed finish events, causal personal reopen events, stale-write protection and conflict handling. Both clients show all pending/active/finished/reopened participants and retain identity privately per review. Completion and approval are independent. The PDF includes the roster, statuses, timestamps and complete finish/reopen history. This remains self-asserted identity and needs no app registration or identity service.

New restricted packages additionally require `reviewer-invitations-v1`. Both toolboxes expose Add reviewers only to the initiator; shared writer and reader admission reject ordinary-reviewer invitations. Independent `reviewer.invited` files extend a review-wide, order-independent membership union without touching the initial manifest, HTML binding, completion records or current approval quorum. Added reviewers' events and verification receipts retain explicit invitation dependencies. Duplicate/concurrent invitations count once in progress but remain audit history. PDFs list every invitation with the initiator, time and event ID. OneDrive/filesystem sharing remains a separate administrative step, and existing capability-absent reviews are not silently upgraded.

The framework-neutral core contract and the portable-product requirements are now separated. Core validity does not require executable HTML or `.gitattributes`; the portable profile requires a review-bound launcher, byte-preserving Git attributes, sanitized rendering and offline PDF export while keeping all review state in the core package. Extension declarations are capability-bound, immutable and non-state-affecting in this version; undeclared or state-affecting semantics fail closed.

## Concrete remaining implementation limitations

These are release blockers under the full professional specification, not claimed completed work:

1. Mermaid rendering is serialized, cached and source-size limited. The caller now stops waiting after 20 seconds, obsolete document renders are cancelled and late tasks cannot overlap a newer Mermaid render. However, Mermaid still executes its DOM-dependent renderer on the UI thread; an already executing library call is not forcibly terminated in a worker. Configuration directives/front matter are explicitly rejected.
2. Creation/capture accepts cancellation before final revision publication, aborts remote capture, drains started file work, and retains exact checkpoints. Participant rendering, full audit, SVG decode, PDF preparation and PDF generation now observe cancellation before the publication boundary; cancellation publishes no `export.created` evidence. Once final publication starts it completes and reports the actual outcome. Source-application cancellation and the complete CLI error-class contract remain incomplete.
3. Native containment checks reject links/junctions and recheck paths, but Node pathname operations cannot prove immunity to every adversarial parent-directory swap. Source edits now stage and verify a separate file, preserve POSIX permission bits and original bytes in the private recovery journal, recheck source/acceptance, and replace the directory entry rather than stream over live source. Tests cover partial staging, changed source, new rejection, unrelated staging bytes and publication failure after replacement. Power-loss durability, concurrent external editor races, and local Windows replacement/ACL semantics still require qualification; SMB semantics are excluded and untested. No cross-process compare-and-swap is claimed.
4. Optional presentation extensions require `presentation-profiles-v1`, an immutable schema declaration and retained schema evidence; the implemented Slidev profile exercises that workflow. Unsupported state-affecting extensions are rejected. Generic conformance fixtures for independently implemented optional presentation profiles are still missing.
5. The client has bounded in-session caches, not a qualified persisted cold-start cache. Full-history audit memory and the complete performance workload remain unqualified.
6. Diagram zoom, search, paged history and keyboard-selectable semantic targets are implemented. Full navigation/accessibility and the complete formatted-selection corpus remain to be qualified; passing the repeated-phrase test alone is not comprehensive anchor assurance.

## Windows policy and release decision

Windows testing is CI-only. Run 4842206, commit `7a2ebb9`, passed all Linux validation/packaging and Windows core tests, the browser storage probe, both browser integration scenarios and the VS Code extension-host test. Windows then failed to provision its disposable SMB share (`New-SmbShare: Access is denied`), so no SMB or real native folder-picker tests ran; Windows audit/packaging were skipped in that run.

On 2026-09-08 the user confirmed that a CI-only SMB share cannot be arranged and requested skipping it. Both CI and release validation now exclude SMB qualification, recording it as **untested, not passed**. Fixtures are retained but not scheduled. The exclusion covers only SMB; real local Windows browser folder grants and remaining permission/restart scenarios still require evidence. Neither origin-private browser handles nor the native storage bridge establishes that evidence. See the [scoped acceptance exclusion](ACCEPTANCE.md#smb-qualification-exclusion).

The professional pilot remains on hold until the concrete blockers and all non-excluded required gates are closed. The SMB exclusion does not waive any other requirement or establish SMB compatibility.

`release-qualification.json` explicitly keeps professional-pilot and 0.6 publication approval disabled and records the SMB exclusion. Publication classification does not establish qualification. The workflow runs browser/extension checks on local storage and refuses to overwrite existing release assets. The default qualification command refuses both professional-pilot and publication approval for this development version.
